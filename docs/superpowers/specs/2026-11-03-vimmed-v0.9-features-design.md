# vimmed v0.9.0: feature design

Date: 2026-11-03
Status: reviewed (builder check done), awaiting owner approval
Scope: features and behaviour only. The tech stack is deliberately left for a separate decision.

## Hypothesis

We believe moon_edit's editing model (vim bindings, markdown rendered in place with element-level
reveal) can be delivered as a single-file, one-window-per-process editor for macOS and Linux that
starts fast enough to be launched from the shell the way vim is, and that nothing from moon_edit's
knowledge-base features (collections, indexing, search across notes, backlinks, sync) is needed for
that use.

Evidence for the belief: the owner edits markdown in vim day to day and wants moon_edit's live
rendering and inline images there, but moon_edit is a cross-platform knowledge-base app built around
collections and an index, which is the wrong shape for `editor file.md` from a terminal. Dropping
iOS, iPad and Android frees the stack choice to optimise for desktop start-up and native feel.

If true: `vimmed notes.md` puts an editable, rendered document on screen quickly enough that it
replaces vim for markdown work, including as git's `core.editor`, without the owner reaching back to
moon_edit or vim for missing features.

This could turn out false in specific ways: start-up may be too slow on the chosen stack for
shell use; in-place rendering may need state or infrastructure (an index, a long-lived process)
that a one-shot process cannot afford; or the owner may keep reaching for a dropped feature.

## Method

1. Build v0.9.0 to this spec.
2. Measure cold start: time from pressing Enter on `vimmed file.md` to the first frame in which
   the document's text is rendered and accepts input. *(Builder's call:)* images may finish loading
   after that frame without the layout jumping (reserve their space); time to all images painted is
   recorded separately and has no threshold in 0.9.0. Use a 1,000-line markdown file with headings, lists,
   a table, two code blocks and two local images. 20 runs per platform (macOS on Apple Silicon,
   one Linux desktop under Wayland), median and p95.
3. Measure keystroke latency in Insert mode on the same file: key event to painted glyph, p95.
4. Dogfood for two weeks: vimmed as `core.editor` and as the default way to open `.md` files.
   Keep a reach-back log: each time the owner opens a markdown file in vim or moon_edit instead,
   note why.

Evidence against the hypothesis: start-up misses the threshold below on either platform; or the
reach-back log shows repeated reaches for a feature this spec drops (as opposed to bugs in a
feature it keeps).

## Desired outcome

Thresholds confirmed by the owner on 2026-11-03.

- Cold start: median at or under 250 ms, p95 at or under 400 ms, on both platforms.
- Keystroke latency: p95 at or under 16 ms (one frame at 60 Hz).
- After two weeks of dogfooding, vimmed is still the configured `core.editor` and default `.md`
  opener, and the reach-back log has no more than two entries caused by a feature this spec drops.
- Qualitative: the owner describes it as feeling like "vim, but rendered", not like opening an app.

## Intent

vimmed is a sibling of moon_edit, not a replacement. moon_edit lives on as the full knowledge-base
app. vimmed takes moon_edit's editing experience and puts it behind a shell command:

    vimmed notes.md

It opens one native window on that one file. It is minimal and calm to look at, and as quick to
start as practical.

## Goals

- moon_edit's vim editing and in-place markdown rendering, at parity (detailed below).
- Launched from the shell, one file per window, usable as `$EDITOR` / `core.editor` with no flags.
- Native window on macOS and Linux.
- Minimal "zen" presentation: the document is the whole UI.
- Start-up fast enough to replace vim for markdown.

## Non-goals

- iOS, iPadOS, Android, Windows.
- File management of any kind: no file browser, folder navigation, rename, move or delete.
- Anything that needs knowledge of more than one file: collections, indexes, full-text search
  across files, backlinks, tags, quick switcher.
- Sync, encryption, accounts.
- Tabs or multiple documents per window.
- A settings screen.
- Markdown moon_edit never supported: footnotes, YAML frontmatter, reference links, autolinks,
  setext headings, indented code blocks, HTML blocks.

## Anti-goals (failure even if every feature works)

- Opening noticeably slower than moon_edit, or feeling like launching an app rather than an editor.
- Losing unsaved work because a terminal closed, a process was signalled or the app crashed.
- Silently changing a file on disk the user did not ask to write.
- Chrome creeping back in: toolbars, sidebars, panels, floating command boxes.

## Constraints

- macOS and Linux only. Linux must work under Wayland and X11.
- moon_edit's behaviour is the reference for anything this spec says "as moon_edit". Source:
  `/Users/bawdo/working/projects/moon_edit` (Flutter/Dart; `lib/vim/`, `lib/editor/`,
  `lib/search/`, `lib/services/inline_parser.dart`, `lib/widgets/vim_cheat_sheet.dart`). vimmed
  is a separate codebase and need not share code with it.
- Vim-like file semantics: the file on disk changes only when the user writes it.
- **The project name is a placeholder and must be cheap to change.** "vimmed" (and every derived
  form: command name, app bundle name and identifier, window title, config and state directory
  names, recovery path, usage text, `--version` output) comes from one definition in the build. A
  rename is a one-line change plus a rebuild, with no hand edits scattered through code, docs
  strings or packaging. The implementation plan must include a task that proves this by renaming
  to a throwaway name, building, and checking that the old name appears nowhere in the outputs.
- **All colours and styles are tokenised.** Every colour, font family, font size, weight, spacing
  value, radius, line height and column width used by the UI comes from a named design token
  (e.g. `color.text`, `color.status.dirty`, `space.column`, `font.mono`). No literal colour or size
  values in view code. Light and dark themes are two token sets over the same names. Tokens live
  in one place in the source, and the config file can override individual tokens (section 10). The
  implementation plan must set up the token layer before any UI is built.

## Approaches considered

These are the behavioural choices made in brainstorming. The tech stack is separate.

**Shell behaviour: wait vs detach.** Detaching by default (gVim, VS Code, Sublime, Zed) breaks
`$EDITOR` until the user learns a flag; gVim's "empty commit message" footgun is the classic case.
Waiting by default (vim, Neovide since 0.13) works as `$EDITOR` out of the box. **Chosen: wait by
default**, with `-b` / `--background` to detach.

**Process model: shared instance vs one process per window.** VS Code, Sublime and Atom route files
into an already-running instance, which is why their `--wait` waits on the wrong window (users
close the tab and git keeps hanging). **Chosen: one window, one process, per file**, which removes
that failure class and puts the pressure on cold start, already the top constraint.

**Terminal lifetime: GUI as child of the shell vs launcher plus detached GUI.** A GUI that is a
child of the shell dies when the terminal closes (Neovide issue #402, gVim `-f`). **Chosen: a thin
launcher that starts a fully detached window process and waits on it.** The terminal can let go of
vimmed; only the window can end it.

**Save model: vim vs autosave.** **Chosen: vim**: disk changes only on write. Autosave exists as an
opt-in setting, off by default.

**Visual direction.** Three mockups were compared (A: paper with no chrome, B: quiet bar, C: dark
focus with dimming). **Chosen: B, quiet bar.** Mockups:
https://claude.ai/artifact/7sBJJfTXYwGSPf8fAZbHBC

## Feature specification

### 1. Command line and process model

| Invocation | Behaviour |
|---|---|
| `vimmed FILE` | Opens FILE in a new window. The launcher waits until that window closes. |
| `vimmed -b FILE` / `--background` | Opens the window; the launcher exits immediately with 0. |
| `vimmed --view FILE` | Opens in reader view (section 7). Combines with `-b`. |
| `vimmed` (no file) | Prints usage to stderr, exits non-zero. No window. |
| `vimmed DIR` | Error to stderr, exits non-zero. No window. |
| `vimmed --help`, `--version` | As usual. |

- Every invocation is its own launcher and its own window process. There is no shared running
  instance.
- The launcher starts the window as a fully detached process (own session, like `setsid`) and waits
  on it.
- Terminal closes (SIGHUP to the launcher): the launcher dies, the window carries on.
- Ctrl+C in the waiting terminal (SIGINT): the launcher exits and the shell gets its prompt back.
  The window carries on. This is "stop waiting", not "quit". *(Builder's call:)* the launcher exits
  130, the shell convention for SIGINT, so a waiting git aborts the commit rather than committing a
  half-written message.
- Window process exits: the launcher exits with the window's exit code (see Quit commands).
- Window process disappears abnormally (crash, kill): the launcher notices and exits non-zero. It
  never hangs.
- macOS: the window process is a proper app bundle so focus and Dock behaviour are native. The
  `vimmed` launcher is a separate command on PATH.
- macOS Finder, double-click and `open`: Launch Services delivers the file to an already-running
  instance. That instance spawns a new, independent window process for the file (not tied to any
  launcher), so the one-process-per-file model holds whichever way a file is opened. Several Dock
  icons when several files are open is accepted. Linux `.desktop` launching starts a process per
  file directly.

**Same file opened twice** (vim's swap-file behaviour). Each window process holds a lock record
for its file in the state directory (process id plus absolute path). A second open of a file that
another live process holds shows a status-line prompt:
`already open in another window (pid N): [o]pen read-only [e]dit anyway [q]uit`. Edit anyway
proceeds; each window then has its own recovery copy (5.2) and sees the other's writes as external
changes (5.3). A lock whose process is gone is stale and is ignored, which is also how a crashed
session's recovery copy is found.

**Missing file.** *(Builder's call, made in the spec.)* As vim: a path that does not exist opens an
empty document titled with that name; the file is created on first write. The parent directory must
exist; if it does not, the write fails with the OS error in the status line.

### 2. Window and look (direction B)

- **Title bar:** slim, native. Shows the file name only. Unsaved changes: macOS shows the standard
  "edited" dot in the close button; Linux prefixes the title with `•`.
- **Page:** one centred text column, about 660 px wide (configurable), sans-serif body, monospace
  for code, inline code and revealed markdown syntax. No sidebar, tabs or toolbar.
- **Status line:** thin bar along the bottom, monospace, small. Left to right: mode (e.g. `NORMAL`,
  `INSERT`, `VISUAL`, `V-LINE`), file name, `changes not saved` (amber) when dirty, any disk warning
  (`file changed on disk`, `file no longer on disk`, `read-only`). Right-aligned: `line:column`.
- **Command line:** `:` commands and `/` `?` searches are typed into the status line, vim style.
  Messages (`reloaded from disk`, errors, `written`) appear there and fade. No floating dialogs for
  these.
- **Theme:** follows the OS light/dark setting live. Dark is direction B in dark colours.
- **Help:** `:help` shows moon_edit's cheat sheet as an overlay, dismissed with Esc.

### 3. Vim editing (parity with moon_edit unless noted)

| Area | Included |
|---|---|
| Modes | Normal, Insert, Visual, Visual Line |
| Motions | `h j k l w b e 0 ^ $ gg G` |
| Operators | `d c y` with motions; `dd cc yy C D` |
| Actions | `x p P u Ctrl+R`; insert entries `i a o O I A` |
| Counts | `3j`, `3dd`, `5G`, `[N]x`, `[N]p`. Compound counts (`2d3w`) not supported, as moon_edit |
| Repeat | `.` |
| Registers | Unnamed register synced with the system clipboard (as moon_edit). **New:** named registers `"a`..`"z`, shared between all windows through a state file (like vim's viminfo), so `"ayy` in one file and `"ap` in another works |
| Text objects | `yic` / `dic` / `cic` (inner code block) |
| Search | `/ ? n N`, incremental, highlight all, smartcase, wraps with a "search wrapped" message |
| Substitute | `:s` and `:%s` with flags `g i c n` |
| Lists | Tab / Shift+Tab indent and outdent; Enter continues lists and exits on an empty item |
| Tasks | `gx` and Ctrl+Space toggle a task checkbox |
| Tables | `:table N M`, `:table` (grid picker), Tab / Shift+Tab between cells, Enter moves down in Insert, `ta tA td tD tc tC tx t> t< t=` |
| Mouse | Click places the cursor; drag or double-click enters Visual |

### 4. Write, quit and reload commands

| Command | Behaviour | Exit code |
|---|---|---|
| `:w` | Write. Refuses if the file changed on disk since read (see 5.3) | |
| `:w!` | Write even if the file changed on disk. Does not force permissions | |
| `:q` | Close. Refuses with a message if there are unsaved changes | 0 |
| `:q!`, `ZQ` | Close, discarding changes | 0 |
| `:wq` | Write, then close | 0 |
| `:x`, `ZZ` | Write only if changed, then close | 0 |
| `:cq` | Close without writing, signal failure (git aborts the commit) | non-zero |
| `:qa`, `:qa!`, `:wqa` | Same as `:q`, `:q!`, `:wq` (single window; accepted for muscle memory) | as above |
| `:e!` | **New.** Discard changes and reload from disk | |
| Cmd+S / Ctrl+S | Same as `:w` | |
| Window close (Cmd+W, close button, WM close) | Same as `:q`, but asks (save / discard / cancel) instead of refusing | 0 |

Each window is its own process, so these close this window only.

### 5. File handling

**5.1 Saving.** Only on explicit write. Autosave is an opt-in setting (off by default); when on, it
writes after a short idle pause. *(Builder's call:)* writes are atomic (write to a temporary file in
the same directory, then rename), preserve the file's existing line endings (LF or CRLF) and its
trailing-newline state, and preserve file permissions. Text is UTF-8.

**5.2 Recovery file.** While there are unsaved changes, a recovery copy is written periodically and
on SIGTERM. *(Builder's call:)* it lives under `$XDG_STATE_HOME/vimmed/recovery/` (default
`~/.local/state/vimmed/recovery/`, same on macOS), keyed by the file's absolute path plus the
owning process (so two windows on one file never share a copy), never next to the file, so it
never ends up in a git repository. It is deleted on a successful write or a
deliberate discard. Opening a file that has a newer recovery copy offers, as a status-line prompt
(`recovery copy found: [r]estore [d]iscard [c]ompare`): restore, discard, or compare.
*(Builder's call:)* compare opens the recovery copy in a second, read-only reader-view window
titled `<name> (recovery)`; the prompt stays open in the original window until the user picks
restore or discard. No diff view in 0.9.0.

**5.3 External changes** (git checkout, formatter, another editor).

| Situation | Behaviour |
|---|---|
| Changed on disk, no unsaved changes | Reload quietly, keep the cursor on the same line, status message `reloaded from disk`. `u` undoes the reload. |
| Changed on disk, unsaved changes too | No reload. Status shows `file changed on disk` beside `changes not saved`. `:w` refuses, `:w!` overwrites, `:e!` reloads. |
| Deleted or moved | Text kept. Status shows `file no longer on disk`. `:w` writes it back to the original path. |
| Becomes unreadable or read-only | Status says so. `:w` fails with the OS error. `:w!` does not force permissions. |

### 6. Markdown rendering (parity with moon_edit)

Rendered in place, with element-level reveal: only the element under the cursor shows its raw
syntax; nothing else on the line moves.

- Headings (ATX), bold, italic, strikethrough, inline code, the 17 CommonMark escapes.
- Links `[text](target)`: clicking opens it (Cmd/Ctrl+click while in Insert mode). See section 8.
- Nested lists, ordered and unordered; task lists.
- Nested blockquotes.
- Fenced code blocks with syntax highlighting and auto-close of the fence.
- Horizontal rules (`---`, `***`, `___`).
- Tables, rendered as a grid.
- Images `![alt](path)`, rendered inline. *(Builder's call:)* local paths only, resolved relative to
  the file's directory; remote URLs show the alt text and URL as a link, with no network fetch.
  Missing images show a placeholder with the alt text.

### 7. Reader view

The same window with the cursor and status line hidden, everything fully rendered and read-only.
Opened with `--view`, toggled in-app. *(Builder's call:)* the toggle key is `Cmd/Ctrl+Shift+R`,
since a Normal-mode letter binding would clash with vim.

### 8. Links

- External URLs open in the system browser.
- A link to another markdown file (relative to this file's directory) opens it in a **new vimmed
  window that is not tied to any launcher**. The original launcher keeps waiting only on its own
  file.
- *(Builder's call:)* a link to any other local file opens with the system handler (`open` /
  `xdg-open`).
- Cmd/Ctrl+L inserts a link: a small prompt for URL or path (no note picker). Selected text becomes
  the link text.

### 9. Non-vim mode

When vim mode is off in config: standard native editing keys. Cmd/Ctrl+B bold, Cmd/Ctrl+I italic,
Cmd/Ctrl+K and Cmd/Ctrl+L link, Cmd/Ctrl+Z / Shift+Z undo and redo, Cmd/Ctrl+F opens a find bar with
match counter and wrap indicator (as moon_edit). The status line stays, without a mode indicator.
`:` commands are not available; quit is window close.

*(Builder's call:)* the situations that need `:w!` or `:e!` in vim mode are handled with
status-line prompts in non-vim mode, never floating dialogs. Saving over a file changed on disk
prompts `file changed on disk: [o]verwrite [r]eload [c]ancel`. The recovery prompt (5.2) is the
same in both modes.

### 10. Configuration

A single file at `~/.config/vimmed/config.toml` (honouring `$XDG_CONFIG_HOME`, same path on macOS
and Linux). Missing file means defaults. Settings:

| Key | Default |
|---|---|
| `vim` | `true` |
| `autosave` | `false` |
| `font.body`, `font.mono`, `font.size` | platform sans, platform mono, 16 |
| `column_width` | about 660 px |
| `theme` | `system` (also `light`, `dark`) |

A `[tokens]` table (and `[tokens.light]` / `[tokens.dark]`) overrides individual design tokens by
name, e.g. `"color.status.dirty" = "#B35C00"`. Unknown token names are reported in the status line
and ignored.

A bad config file shows a status-line message on start and falls back to defaults; it never stops
the file from opening.

## Dropped from moon_edit

Collections, home and collection tabs, folder navigation, file operations, folder picker, quick
switcher, note search dialog, search view, backlinks panel, link scanner, tags, SQLite index and
migrations, macOS security-scoped bookmarks, settings screen, `:img` and the insert-image picker,
the about dialog, Google Drive sync, encryption and the planned Nexus and Orbit features, iOS and
Android.
