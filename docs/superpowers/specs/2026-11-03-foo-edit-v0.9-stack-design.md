# foo_edit v0.9.0: tech stack design

Date: 2026-11-03
Status: reviewed (builder check done), awaiting owner approval
Scope: the tech stack, process model and performance approach for v0.9.0. Features and
behaviour are set by `2026-11-03-foo-edit-v0.9-features-design.md` (the feature spec), which this
document does not change except where a section is explicitly marked as a proposed amendment.

## Hypothesis

We believe the full v0.9.0 feature set can be delivered within the feature spec's thresholds on
one shared Rust core and CPU renderer, with thin native shells (AppKit through `objc2` on macOS,
GTK4 on Linux) and two binaries (a libc-only launcher and a window process). Evidence: a
throwaway spike with a deliberately crude renderer met the thresholds on both reference machines
once three presentation costs were found and removed (CGImage layer contents on macOS,
whole-window cairo uploads in GTK, whole-window damage):

- macOS (Apple Silicon): cold start median 165 ms, p95 176 ms; keystroke p95 4.3 ms.
- Linux (Omarchy, i7-7700HQ, 4K 60 Hz at scale 2), GTK with the GL renderer: cold start median
  213 ms, p95 227 ms; keystroke p95 14 ms from real key events.

If true, the real editor (vim engine, full markdown rendering, tables, ten grammars, config,
recovery, locks) fits on top of that skeleton without either platform crossing a threshold.

This could turn out false in specific ways:
- The real start-up work (config, lock and recovery scan, real parser, fallback fonts, vim
  engine) costs more than the 37 ms of median headroom Linux GTK has, and nothing short of a
  resident process or dropping GTK recovers it.
- Real per-keystroke work (incremental parse, re-highlight, table relayout, vim engine) plus
  GTK's frame-clock wait pushes Linux keystroke p95 past 16 ms. The spike's GTK margin is 2 ms
  and its p99 was 48 ms.
- The IOSurface and strip-texture presentation patterns stop paying off once the screen carries
  real content (images, tables, highlighted code), for example because more of the screen is
  damaged per keystroke than the spike's single edited line.

## Method

1. Build v0.9.0 to the feature spec on this stack. Port the spike's measurement harness (launch
   timestamps, first-frame and on-glass marks, keystroke split into wait, draw and render) into
   the codebase as a permanent developer tool, before the first feature lands.
2. Measure at three checkpoints: after the shells and renderer skeleton, after the vim engine and
   full markdown rendering, and at feature complete. Each checkpoint runs the feature spec's
   1,000-line fixture on both reference machines: 20 cold starts, and at least 500 manually typed
   keystrokes (real keyboard timestamps), reporting p50, p95, p99 and on-glass times.
   *(Builder's call:)* cold starts on macOS run on the development Mac; manual typing runs on
   macOS, and all Linux runs on the Omarchy laptop, are done by the owner. macOS on-glass timing
   needs its own method (display-link timestamps or a 240 fps camera) and is a harness task.
   Work that does not depend on a checkpoint carries on while a checkpoint waits for the owner.
3. Evidence for: every checkpoint inside the thresholds with each start-up stage within the
   budget in "Performance budget" below. Evidence against: a checkpoint over a threshold that
   cannot be brought back by optimising our own code, so that the fix would need a resident
   process, a raw Wayland shell, a GPU renderer or a different text stack.
4. *(Owner decision:)* checkpoints are review gates. A miss that our own code cannot recover stops
   the work and goes back to the owner; no fallback shell is pre-approved or kept building in the
   meantime.

## Desired outcome

- At feature complete, on both reference machines: cold start median at or under 250 ms and p95
  at or under 400 ms, measured to frame hand-off with on-glass recorded (Linux measured with GTK,
  not the raw Wayland fallback).
- Keystroke p95 at or under 16 ms from key event to frame handed to the compositor, on both
  machines, from at least 500 manually typed keys. On-glass p95 recorded alongside and at or
  under 2.5 refresh periods (about 42 ms at 60 Hz). See "Proposed amendments" for why the
  threshold is stated this way.
- All editing and rendering logic lives in the shared core and is testable without a window.
  Checkable by line count: each platform shell is under 2,500 lines of Rust at feature complete.
- The rename test from the feature spec passes: changing the one name definition and rebuilding
  leaves the old name nowhere in the built outputs.
- Qualitative: the owner, reviewing AI-written changes in vim, can follow any shell or core
  module without needing to understand the other platform's toolkit.

## Intent

The feature spec asks for an editor that opens from the shell as fast as vim and feels native and
calm. It leaves the stack open, weighted by the cold-start threshold. This document records the
stack chosen in brainstorming with the owner, the evidence from the spike and the research behind
it, and the patterns the build must follow so the spike's measured performance survives contact
with real features.

## Goals

- Meet the feature spec's thresholds with margin on both platforms.
- One shared core holding everything that is not windowing: document model, markdown parsing and
  reveal, vim engine, commands, file handling, config, design tokens, rendering.
- Thin, readable platform shells.
- Works across Linux distributions, not just Arch: Wayland primary, X11 best effort.
- A stack that is stable enough for AI-assisted work and maintainable by the owner in vim.

## Non-goals

- Windows, iOS, Android (as the feature spec).
- GPU rendering in v0.9.0. The spike shows CPU raster is fast enough at 4K; a GPU path is a
  later option behind the same presentation boundary.
- A resident or single-instance process. The feature spec's one process per file rules it out,
  even though it is the usual way GTK apps hide start-up cost.
- Flatpak or Snap packaging in v0.9.0 (sandboxing fights `$EDITOR` use).
- Reusing moon_edit's Flutter code. moon_edit stays the behavioural reference only.

## Anti-goals (failure even if every feature works)

- A start-up path that only meets the thresholds on the owner's machines because of a warm cache
  that a first run on a fresh install would not have, without the first-run cost being measured
  and stated.
- Platform shells that grow their own copies of editing or rendering logic.
- Performance that regresses silently: every checkpoint is measured, not assumed.

## Constraints

From the feature spec and the owner:

- macOS and Linux only. Linux must run under Wayland (primary) and X11 (best effort) and on
  mainstream distributions, not only Arch.
- A fast compiled language (owner): Rust.
- Two binaries, built and shipped together (owner decision after the spike): `foo_edit` and the
  window process. The user only ever types `foo_edit`.
- The project name comes from one definition in the build; every colour and style is a design
  token the config file can override (feature spec).
- The owner edits in vim and reviews AI-written code; APIs that churn fast are a cost.

## Approaches considered

**Language: Rust vs Zig.** Zig cross-compiles easily and builds small binaries, and Ghostty proves
the shape. But it is pre-1.0 and breaks its standard library between releases, so AI-written Zig
often targets an old release, and its macOS story means calling the Objective-C runtime by hand.
Rust has stable tooling (cargo, rust-analyzer in vim), mature bindings (`gtk4-rs`, `objc2`) and
packaging tools. **Chosen: Rust** (owner).

**Shell architecture.**
- A: each platform's own text view (TextKit 2, GtkTextView). Writes the hardest part (reveal,
  tables, images) twice against two text systems that fight custom per-line rendering.
- B: one shared CPU renderer with thin native shells.
- C: GPUI (Zed's framework). Least code, but pre-1.0, churns with Zed's needs, thin docs, less
  native.

**Chosen: B** (owner). It is also how moon_edit already works (custom per-line layout).

**Linux shell: GTK4 vs raw Wayland.** Measured head to head in the spike. Raw Wayland
(smithay-client-toolkit, shm buffers) started in 68 ms against GTK's 147 to 234 ms and handed
keystrokes off in 5 ms (p95) against 14 ms, but on-glass p95 was the same 40 ms for both on a
60 Hz panel, because GTK's wait happens in the app and raw Wayland's in the compositor. Raw
Wayland drops X11, input methods for non-English keyboards, clipboard and GNOME window
decorations, all of which we would then build. **Chosen: GTK4** (owner), keeping the shell thin
so raw Wayland stays a later option.

**Binaries: one vs two.** One binary that forks without exec on Linux is proven by kitty, but
only while the process is single-threaded with no GLib initialised, it needs a pipe handshake
against a SIGHUP race kitty shipped as a bug, and it gives up the 2.8 ms launcher. macOS forbids
fork without exec. **Chosen: two binaries** (owner): same time to window, none of the fork-safety
reasoning.

**Text layout: cosmic-text vs parley.** Both are active and both shape with HarfRust. cosmic-text
is what the spike measured and has a simple per-buffer model, but it is effectively one
maintainer, breaks minor versions often and lags its upstream crates. parley has several
maintainers and Bevy has moved to it, but it churns faster still. **Chosen: cosmic-text behind a
thin internal layout trait** (my call), with a head-to-head benchmark against parley as an early
task (see "Open items").

## The stack

### Workspace layout

A cargo workspace. Only the two shell crates depend on a GUI toolkit.

| Crate | Contents | Depends on |
|---|---|---|
| `core` | document model, our own markdown line classifier and inline parser (a port of moon_edit's behaviour, not a tree-sitter parse), reveal rules, vim engine, commands, search and substitute, file handling (atomic writes, external changes, recovery, locks), state directory, config (TOML) and design tokens | no GUI, no fonts |
| `render` | line layout and paint into an RGBA buffer, damage tracking, font loading and fallback, highlighting, images | `core`, cosmic-text, tiny-skia, swash, tree-sitter, image |
| `shell-mac` | window, input, clipboard, theme, IOSurface presentation, Finder router | `core`, `render`, objc2 crates |
| `shell-gtk` | window, input (including input methods), clipboard, theme, strip-texture presentation | `core`, `render`, gtk4 |
| `launcher` | `foo_edit`: argument parsing, spawn, wait, signals, exit codes | libc only |
| `xtask` | packaging, name templating, rename test, benchmarks | build-time only |

The window binary is built from whichever shell crate the target uses.

### Process model

- `foo_edit FILE` is the launcher. It links only libc (the spike measured 2.8 ms to `main` on
  Linux, against 43 ms when the launcher linked GTK). It starts the window process with
  `posix_spawn` and `POSIX_SPAWN_SETSID`, which puts the child in its own session before it
  executes, so there is no SIGHUP window to race (glibc 2.26+, and defined in the current macOS
  SDK). The child's stdio goes to `/dev/null` (or a log file in the state directory), so a closed
  terminal can never make it fail on a write.
- The launcher waits with `waitpid`, passes the window's exit code through, maps a crash signal
  to 128 + n, and exits 130 on SIGINT (the feature spec's "stop waiting"). Launcher failures use
  their own reserved exit codes, following footclient.
- `-b` returns once the window process has started.
- Linux: the window binary lives in the package's private directory (for example
  `/usr/lib/<name>/`), and the launcher finds it at a path fixed at build time, falling back to
  next to `current_exe()` for development builds.
- macOS: both binaries live in `<Name>.app/Contents/MacOS/`, and the window binary is the bundle's
  executable. The CLI is a symlink from a PATH directory to the bundle's launcher. A window
  process started directly by the launcher bypasses Launch Services.
- macOS Finder, double-click and `open`: Launch Services delivers files to a running instance via
  `application:openURLs:`. That instance acts as a thin router: it spawns one sibling window
  process per file (the bundle executable with the path as an argument) and yields activation to
  it, then exits when it has no window of its own. Whether a directly spawned process changes
  which instance Launch Services picks next is unverified and is tested early.
- Activation: macOS 14 activation is cooperative, so a window started from the user's active
  terminal is activated normally (seen in the spike). A window started from a background process
  may not become key, which is expected.

### Rendering core (shared)

- CPU raster into one premultiplied RGBA buffer (tiny-skia for fills and images, our own glyph
  blending from swash's cache).
- Each source line is its own layout object. Only lines on screen are shaped; the rest are
  shaped on demand.
- Element-level reveal: the element under the cursor shows its raw syntax and the rest of the line
  shifts to make room, with no overlap (owner decision, matching moon_edit, Obsidian, Typora and
  Bear). This clarifies the feature spec's section 6: "nothing else on the line moves" means the
  other elements on the line stay rendered, not that no glyph changes position (see "Proposed
  amendments"). Reveal happens only when the cursor is strictly inside an element, and on mouse-up rather
  than mouse-down. Hanging block prefixes (`#`, `>`, list markers) in the left margin, as iA
  Writer does, are an option for the builder to evaluate.
- Damage is tracked as a list of row ranges, kept separate (an edited line and the status bar must
  not merge into the whole window; in the spike that bug cost 20 ms per keystroke on Linux).
  Presentation code consumes the ranges.
- Images: dimensions read from the file header at start-up so space is reserved; decoding happens
  on a worker thread and paints later, with no layout jump (as the feature spec).

### macOS presentation

- A layer-hosting view (we own the layer tree; Apple warns that a view may overwrite the contents
  of a layer that backs it).
- Two IOSurfaces (BGRA, premultiplied), swapped as the layer's contents on each present.
  Assigning the same surface again tells Core Animation nothing, so swapping is required. Each
  surface is two frames stale when reused, so each present copies the union of this frame's and
  the previous frame's damage (the spike already does this).
- Surfaces are tagged sRGB with `kIOSurfaceColorSpace`; tokens are authored in sRGB and the
  compositor matches to P3 displays.
- Never set a `CGImage` as layer contents per frame: it cost about 12 ms per commit in the spike,
  and softbuffer measured 13 to 20 ms on the same path. For the same reason, do not use softbuffer
  for presentation.
- Frame pacing with `NSView.displayLink(target:selector:)`, paused when there is no damage.
  This sets a **macOS 14 minimum** (CVDisplayLink is deprecated from macOS 15).

### Linux presentation (GTK4)

- A small custom widget whose `snapshot()` appends one `GdkMemoryTexture` per 128-pixel strip.
  Only strips touched by damage get a new texture; unchanged strips keep the same texture object
  across frames, because GSK caches uploads per texture object and never uploads part of a
  texture. `GdkMemoryTextureBuilder`'s update region (4.16+) only narrows repaint damage, so it is
  optional.
- Key handler updates the model and calls `queue_draw()` directly; no idle or timeout hops.
- Renderer: set `GDK_DISABLE=vulkan` before GTK initialises, as Ghostty does (it reports Vulkan
  initialisation costing hundreds of milliseconds on some systems; in the spike GL started 21 ms
  faster than the default Vulkan). A user-set `GSK_RENDERER` is honoured. Strip `GDK_DISABLE`,
  `GDK_DEBUG` and `GSK_RENDERER` from processes we spawn (link opening). Cairo started fastest
  (147 ms) but composites on the CPU and its keystroke latency is unmeasured, so it is not the
  default until measured.
- No `GApplication` uniqueness (no D-Bus name round trip) and no libadwaita.
- Minimum GTK 4.14 (Ubuntu 24.04 ships 4.14.5; Debian 12's 4.8 is out of scope). Features from
  4.16 and later are behind gtk4-rs version features and checked at run time.
- X11 is best effort: GTK keeps its X11 backend for the whole GTK 4 lifetime though it is
  deprecated; on X11 the GL renderer is the default anyway.
- Input methods, compose and dead keys must be tested on Hyprland and on one compositor without
  text-input-v3.

### Fonts

- Load the configured faces by path, plus a small fixed fallback set per platform (macOS: Apple
  Color Emoji, Apple Symbols, Menlo; Linux: the fontconfig matches for emoji and symbols). The
  spike's missing ☐ came from cosmic-text only falling back among faces already loaded.
- A custom cosmic-text `Fallback`. When a glyph is still missing, ask the OS off the start-up path
  (`CTFontCreateForString` on macOS; a fontconfig charset match on Linux), load the face and cache
  the codepoint-to-file mapping.
- Never scan all system fonts at start-up (about 25 ms plus slower first layout on macOS; about
  315 ms on the Linux laptop).
- Linux: cache resolved font paths in `$XDG_CACHE_HOME/<name>/`, keyed on the fontconfig cache and
  config modification times, so start-up skips fontconfig entirely (33 ms to under 1 ms in the
  spike). First-run cost is measured and reported separately.

### Highlighting

- tree-sitter with tree-sitter-highlight. Grammars: `tree-sitter-rust`, `-go`, `-javascript`,
  `-typescript` (includes TSX), `-ruby`, `-sequel` (the maintained SQL grammar), `-html`, `-css`,
  `-bash`, `-hcl` and `-md` (with block and inline injection). *(Builder's call:)* `-md` only
  colours fenced code blocks tagged `md` or `markdown`; it does not drive document rendering,
  which is `core`'s own parser.
- Query compilation is per language, lazy on first use, on a worker thread (10 ms on the Mac and
  32 to 37 ms on the Linux laptop for Rust alone). Code blocks paint plain on the first frame and
  are coloured on the next; colour changes nothing about layout.
- Highlight only the visible range. Keep each block's parse tree and re-parse incrementally on
  edits.

### Configuration and design tokens

- `core` holds the token table (names, light and dark values). Views read tokens only.
- Config is TOML (`toml` and `serde`), read on start-up; a bad file falls back to defaults with a
  status-line message (feature spec).

### Name from one definition

- One `[workspace.metadata.app]` table in the root `Cargo.toml` holds the name and its derived
  forms (display name, bundle identifier, config and state directory names).
- A shared build script turns it into compile-time constants (window title, usage text,
  `--version`, config and state paths).
- `[[bin]]` names in Cargo cannot be computed, so they stay fixed and neutral. `xtask` renames the
  built binaries during packaging and renders Info.plist, the `.desktop` file, metainfo, the
  PKGBUILD and the `.deb` and `.rpm` metadata from templates.
- The feature spec's rename test runs in `xtask` and in CI.

### Packaging

- macOS: `.app` assembled by `xtask`, with the CLI symlink installed on first run or by a
  documented command. Code signing and notarisation are deferred until distribution beyond the
  owner.
- Linux: `.deb` (cargo-deb), `.rpm` (cargo-generate-rpm) and an AUR PKGBUILD. Both binaries in one
  package.
- gtk4-rs 0.11 needs Rust 1.92 or later, so packages build with a current toolchain, not an older
  distro rustc.

### Performance harness

- Ported from the spike: the launcher passes a start timestamp, the window logs named marks
  (process start, config read, fonts, toolkit init, first paint, first frame handed off, first
  frame on glass from the compositor's presentation feedback, images painted), and keystrokes are
  split into wait, draw and render.
- A bench command runs N cold starts and reports median, p95 and p99.
- Keystrokes are measured from real key events. On Linux, `wtype`'s timestamps use a different
  clock and are only usable for handler-relative numbers, so the bench supports manual typing and,
  later, a small uinput injector that records the monotonic clock as it sends.
- Developer tool only: the release binary keeps the marks behind an environment variable.

## Performance budget (Linux GTK, the tight case)

Medians on the i7-7700HQ reference laptop. Spike figures are from round three (GL renderer,
strips).

| Stage | Spike | Budget |
|---|---|---|
| Launcher to window process `main` (GTK library loading) | about 60 ms | 65 ms |
| Read file, parse, config, lock and recovery scan, fonts | about 2 ms (no config, locks or recovery) | 20 ms |
| GTK init and window creation | about 37 ms | 40 ms |
| Renderer initialisation to first paint | about 77 ms | 80 ms |
| First layout and raster, hand-off | about 37 ms | 40 ms |
| **Total to first frame** | **213 ms** | **245 ms** |

On macOS the spike's first frame took 165 ms, and most of that is AppKit (about 115 ms).
Keystroke: our draw at most 2 ms at p95, GTK render at most 4 ms; the frame-clock wait is the
compositor's.

## Proposed amendments to the feature spec

The feature spec's keystroke threshold is "key event to painted glyph, p95 ≤ 16 ms (one frame at
60 Hz)". At 60 Hz a composited app cannot meet that on glass: a key landing at a random point in
the refresh cycle waits up to 16.7 ms for the next frame, and the compositor shows it a frame
later. The spike measured on-glass p95 of 40 ms for both GTK and raw Wayland. Published
hardware-measured figures for the best editors and terminals at 60 Hz are about 33 to 36 ms on
average.

### Reveal (owner decision, 2026-11-03)

Section 6's "nothing else on the line moves" is read as: other elements on the line stay
rendered while the element under the cursor reveals its syntax, and the rest of the line shifts
to make room with no overlap. The owner chose shifting in brainstorming after the prior-art
review (every editor checked shifts; none overlaps).

### Keystroke threshold (owner confirmed 2026-11-03)

Proposed wording:
- **Threshold:** key event to frame handed to the compositor, p95 ≤ 16 ms, measured from real key
  events over at least 500 keystrokes with randomised gaps.
- **Recorded alongside, with a target:** key event to on-glass (compositor presentation time), p95
  ≤ 2.5 refresh periods (about 42 ms at 60 Hz, 21 ms at 120 Hz).
- **Recorded, no target:** comparison with neovim in foot on the same machine and session.

### Cold-start measurement point (owner confirmed 2026-11-03)

The feature spec's "first frame in which the document's text is rendered and accepts input" is
measured to the moment that frame is handed to the compositor (the same point as the keystroke
threshold), on the first run after the file is in the page cache. The on-glass time is recorded
alongside with no threshold. First-run cost on a fresh install (empty font cache) is measured and
reported separately.

## Risks

- **Linux GTK headroom is thin** (37 ms median at start-up, 2 ms at keystroke p95). Mitigation:
  checkpoints, the budget above, and raw Wayland as a measured fallback that the thin shell keeps
  cheap to switch to.
- **cosmic-text churn and bus factor.** Mitigation: the internal layout trait and the parley
  benchmark.
- **macOS Finder routing** behaviour with directly spawned processes is unverified. Mitigation:
  test it in the first macOS shell task.
- **First-run cost** (font cache empty, fontconfig cold) is not yet measured.
